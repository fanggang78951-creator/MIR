# 翎风/LFM2 素材接入与新服部署平台总路线

> **总目标：** 用户提供完整传奇客户端、配套服务端或 `E:\素材` 一类散装素材；Codex负责首次识别、归类和找出资源链，玄渊平台负责可重复的扫描、校验、编号重映射、候选生成、事务部署、回滚和回读。用户只承担少量不可替代的确认、程序关闭、登录器生成和游戏验收。

**平台范围：** 只支持当前版本翎风/LFM2。不能把“未知格式自动猜测”当成平台能力，也不能把一个供体的数字编号直接复制到另一个新服。

**现有基础：** `E:\XuanYuanDevPlatform` 已有功能卡、包仓库、只读预检、候选包、事务安装/回滚、GUI/CLI绑定构建和 `current-release.json` 发布链；装备模块已有静态图和动作帧链路。本路线扩展现有能力，不创建第二套平台、第二套CLI或第二套事务系统。

## 一、职责边界

### Codex负责“首次理解”

- 判断素材属于装备静态图、人物动作、装备特效、怪物、地图、NPC/UI或未知类别。
- 从供体服务端、客户端和登录器中找出真实引用链，区分资源文件、数据库绑定、文本表和登录器清单。
- 对图片序列、PAK/WZL/WIL及数据库记录做首次配对，指出证据、歧义和缺失依赖。
- 把已经验证的规律写成版本化适配器或部署配方，并补齐测试样本。
- 新格式未闭环前保持“候选/待验证”，不让平台猜测写入正式目标。

### 平台负责“重复执行”

- 只读扫描、增量指纹、去重和来源清单。
- 按已验证适配器解析资源链和依赖闭包。
- 在目标新服中分配 Looks、Shape、资源号、特效号等目标编号。
- 生成候选文件、预览、冲突报告和明确的人工确认项。
- 对服务端、客户端和登录器补丁源执行统一事务，失败回滚。
- 回读目标哈希、数据库记录、帧索引和登录器覆盖情况，生成收据。
- 把同样的配方重复用于后续装备或后续新服，不再逐件手工进入M2配置。

### 用户只做少量操作

1. 选择或提供素材根目录、目标服务端、目标客户端和登录器工程。
2. 在平台无法唯一判断时，从预览候选中确认“用哪一组素材/绑定到哪个物品”。
3. 写入前按提示关闭资源编辑器、客户端或相关进程。
4. 平台提示时生成登录器；暂不尝试自动控制第三方登录器生成器。
5. 进入游戏完成平台无法替代的背包、穿戴、站立、走跑、攻击、内观和地面特效验收。

## 二、唯一权威源与目录边界

### GitHub私有仓库

`fanggang78951-creator/MIR` 作为代码权威源，保存：

- 平台源码、测试、JSON Schema、功能卡和构建脚本；
- 小型脱敏测试夹具及其预期结果；
- 适配器版本、部署配方模板和发布说明；
- 审计记录，不保存密码、私服数据库、完整客户端或大体积商业素材。

第一阶段把当前正式平台的**可维护源文件**导入本仓库的 `platform/` 目录；此后以GitHub工作树为权威源，通过受控同步发布到 `E:\XuanYuanDevPlatform`。不能同时独立修改两份源码。

### `E:\XuanYuanDevPlatform`

作为本机正式运行和资料母库，保存：

- 从GitHub权威源受控同步下来的运行源码；
- `bin` 正式发布物、`current-release.json`、本机证据和构建缓存；
- 大体积素材库、候选包、备份、事务收据和本机配置；
- 不适合进入Git的供体资源与测试客户端。

### 外部素材与目标服

- `E:\素材`、旧客户端和下载包始终是只读来源；平台只记录绝对路径、大小、mtime、SHA-256和来源标签。
- `D:\MirServer`、`E:\11周年` 等是部署目标，不承担平台母库职责。
- 大资源复制到平台库时使用内容哈希去重；原来源不删除、不改名。

## 三、统一数据模型

全流程只维护四种记录，防止Excel、JSON、数据库和界面各自成为一套事实来源。

### 1. 素材接入清单 `source-manifest.json`

由平台只读生成，记录：

- 来源ID、根路径、来源类型、文件清单与SHA-256；
- PAK/WZL/WIL/WIX/WZX/图片/数据库/文本的可确定事实；
- 已识别适配器、未知文件、加密状态和读取阻断项；
- 上次扫描指纹，使未变化目录不重复全量分析。

### 2. Codex判定单 `analysis-decision.json`

由Codex在首次分析后生成，记录：

- 素材类别、依赖关系、配对组、资源用途和证据；
- 置信状态：`verified`、`candidate`、`unknown`、`rejected`；
- 仍需用户确认的最小问题；
- 适用的适配器ID和版本。

判定单只表达已经分析出的事实，不含目标服编号。

### 3. 部署配方 `deployment-recipe.json`

作为“这批素材要变成什么”的唯一业务输入，记录：

- 选择的素材组和目标物品/怪物/地图/UI用途；
- 必须保留的动画帧、坐标、绘制方式和资源依赖；
- 允许平台分配的目标编号范围与冲突策略；
- 用户已确认的歧义；
- 所需服务器、客户端和登录器作用域。

同一配方可以对不同新服重新编译，但不能复用旧目标的数字编号。

### 4. 目标计划与事务收据

- `preflight.json`：目标本次实际编号、变更、阻断项、备份和回滚方案，目标变化即失效。
- `receipt.json`：实际写入前后哈希、备份位置、登录器待办、回读结果和游戏验收状态。

## 五、适配器策略

适配器不是按供体名称无限复制，而是按**资源链类型**复用。

### A. 完整客户端/服务端适配器

输入同时含客户端资源、服务端数据库/文本和登录器工程。平台可提取真实绑定；明月端是第一份已闭环样本。

### B. 散装素材适配器

输入为 `E:\素材` 一类BMP/PNG序列、WIL/WIX、WZL/WZX、PAK或压缩包。没有服务器绑定时，Codex先识别帧组和用途，再形成部署配方；平台不凭文件名自动决定Shape或Looks。

### C. 已有平台母库适配器

复用平台中已验证的装备、地图、NPC/UI等资产，不再重新识别原始来源。

### 首批资源链优先级

1. 装备静态图、人物动作和物品特效的完整闭环。
2. 散装装备图片序列到目标原生资源格式。
3. 怪物外观、动作序列和MonGen/数据库绑定。
4. 地图、雷达小图、MapInfo和原生连接。
5. NPC、对话框、UI和状态图标。

每类只在一个真实样本完成“解析、候选、部署、回滚、游戏验收”后，才提升为可重复平台能力。

## 六、分阶段实施与验收门

### 阶段0：GitHub源码权威化

**目标：** 结束“E盘源码无版本控制、GitHub只有计划”的状态。

- [ ] 对 `E:\XuanYuanDevPlatform` 做源文件/运行数据分类清单和敏感信息扫描。
- [ ] 在GitHub仓库建立 `platform/`，只导入允许列表中的源码、测试、Schema、功能卡、小夹具和构建工具。
- [ ] 建立 `platform-sync-preflight`：比较Git权威源与E盘运行副本，只输出差异。
- [ ] 建立带备份和收据的 `platform-sync-apply`，禁止反向自动覆盖Git权威源。
- [ ] 在原平台完整测试、冻结构建和来源指纹验证通过后，才切换正式发布。

**验收门：** 任一正式EXE都能追溯到Git提交、测试收据和 `current-release.json`；大素材、密码和目标服数据不进入Git。

### 阶段1：只读素材接入与增量清单

**目标：** 平台可以对完整客户端和 `E:\素材` 建立事实清单，但不尝试语义猜测。

- [ ] 扩展现有 `ArtifactLibrary`，增加不复制源文件的扫描模式和增量缓存。
- [ ] 识别文件族、配对文件、压缩包目录、基础图像尺寸、可读索引和加密阻断。
- [ ] 输出紧凑摘要供Codex分析，避免每次消耗Token重扫几万文件。
- [ ] GUI增加“素材接入”功能卡：选择来源、查看变化、导出接入清单。

**验收门：** 对 `E:\素材` 和明月供体各运行两次；第二次未变化扫描必须复用指纹，零目标写入且摘要稳定。

### 阶段2：明月装备端到端垂直切片

**目标：** 用已经游戏验收的武器案例证明统一模型，而非只做一个特效工具。

- [ ] 接入静态图、武器/衣服动作、物品内观与地面特效的完整依赖。
- [ ] 将明月三表链 `EffectImageList → EffectList → EffectItemList` 编译为目标特效号和目标资源号。
- [ ] 保留一物多特效；目标同名资源、编号占用和数据库物品歧义均阻止。
- [ ] 复用现有 `equipment_graphics` 事务，把服务端表、客户端PAK和登录器补丁源纳入同一收据。
- [ ] 先做真实只读预检和候选包；得到单独部署授权后才写目标。

**验收门：** 同一配方可在空白测试目标重复编译；apply、noop、回滚和重新apply均通过；游戏验收覆盖背包、穿戴、内观、站走跑攻和地面特效。

现有子计划：`docs/superpowers/plans/2026-09-22-lfm2-item-effect-migration.md`。它只负责本阶段的特效编译器，不得替代本总路线。

### 阶段3：`E:\素材` 散装装备接入

**目标：** 用户给出散图或资源包，Codex完成一次识别，平台批量完成同类处理。

- [ ] 选择一组武器、一组衣服和一组只有小图/内观的素材作为三种夹具。
- [ ] Codex判定帧分组、方向、动作数量、透明色、坐标和缺失项。
- [ ] 平台生成中文预览表和目标配方，批量转换/追加，不逐件手改。
- [ ] 未满足完整动作要求的素材允许降级为“仅静态候选”，不得伪装成完整装备。

**验收门：** 新增同格式第二批素材时，用户只需选目录和确认配对，平台不再需要改代码。

### 阶段4：怪物、地图和UI适配器

按“一个资源链一个垂直切片”推进，不并行铺开半成品：

- [ ] 怪物：动作资源、数据库外观、刷新/脚本依赖和游戏验收。
- [ ] 地图：地图文件、Tiles/Objects、雷达、MapInfo、落点和连接。
- [ ] NPC/UI：资源号、坐标、脚本命令、登录器同步和显示验收。

**验收门：** 每类均具备真实样本、目标无关配方、只读预检、事务、回滚和游戏验收清单。

### 阶段5：新服部署工作台

**目标：** 把已验证适配器组合成一次新服部署任务，而不是大范围盲目“一键覆盖”。

- [ ] GUI选择来源清单、部署配方、目标服务端/客户端/登录器工程。
- [ ] 汇总跨模块资源号冲突、目标空间、进程占用和密码/登录器待办。
- [ ] 生成单一批次计划，按作用域事务写入并提供整批回滚。
- [ ] 输出游戏验收任务单；用户逐项勾选后才把批次标记为 `verified`。

**验收门：** 对一个干净测试服完成从素材选择到回滚/重装的全流程；正式服仍需单独部署授权。

## 七、Token和人工成本控制

- 平台只把文件族、冲突、缩略图索引和变化摘要交给Codex，不发送全量二进制或重复目录列表。
- 来源清单以根指纹和逐文件SHA缓存；未变化文件不重复读取、截图或分析。
- Codex判定单可复用；只有来源哈希、引擎版本或目标约束变化时才重新分析。
- 图片预览优先生成联系表；一次看一组，不逐帧截图。
- 适配器错误首先复现单个夹具，连续失败时回到数据流和格式证据，不叠加猜测性补丁。

## 八、安全与质量门

- 检测、候选、预检、应用、游戏验收、正式发布是六个不同状态；任何前一状态不能冒充后一状态。
- 预检严格零写入；应用前冻结来源、目标、配方和适配器版本哈希。
- 数据库、服务端、客户端、登录器补丁源必须进入同一事务或明确列为人工待办，禁止“半部署成功”。
- PAK密码只进入本机受保护配置或用户操作，不进入Git、日志、收据和Codex判定单。
- 第三方素材版权和可再分发范围由用户负责确认；平台默认只做本机处理，不上传素材。
- M2和游戏验收由用户操作；平台不自行启动整套引擎。

## 九、当前立即执行顺序

1. 先完成阶段0的只读分类和Git导入候选清单，不立刻移动或覆盖E盘平台源码。
2. 同时把本次明月闭环整理成阶段2的固定夹具、预期结果和适配器契约。

4. 再实现阶段2的明月装备端到端切片；确认通用流水线可靠后，才扩展阶段3。

这四步完成前，不制作“万能识别”宣传，也不把尚未验证的格式放进正式一键部署。
