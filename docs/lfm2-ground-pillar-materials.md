# 翎风地面光柱：黑金「神兵现世」实机通过的制作链

> 2026-09-25 木剑单件验证。本文记录可复用流程及本次证据边界，不收录 PAK 密码、素材二进制或用户私有原画。引擎字段背景另见本地 `LF-M2-014_查看列表信息_光柱特效.txt`；这里不另建一套光柱配置规则。

## 已验证结果与范围

用户在正式游戏中确认：木剑落地后能显示黑金披风人物、金色光柱与底部法阵，青蓝色竖排小字「艾尔登法环·神兵现世」可辨；坐标微调后，木剑与光圈位置正常。这是**单件可见性和落点验收**，不是对 12 帧循环流畅度、拾取消失/再次掉落、其他武器或跨客户端兼容性的完整验收。

本次正式端配置的只读回查值：

| 环节 | 本次值 | 用途 |
| --- | --- | --- |
| `PillarOfLightEffectItemList.txt` | `木剑 → 50001` | 按物品名称绑定光柱定义；不是按某把实例绑定 |
| `EffectImageList.txt` | 零基序号 `37 → 老方.Pak` | 目标端资源编号；不可照搬到其他端 |
| `PillarOfLightEffect.txt` | `50001 / 37 / 0 / 12 / 100 / 0 / -270 / 1 / 1 / 1` | 光柱号、资源号、起始帧、帧数、速度、X、Y、三个绘制标记 |

`-270` 仅是**这套 600×700 画布、当前内容位置与绘制标记**下校准出的 Y 值，不是通用光柱坐标。三个标记保留本次实测组合；单个标记的精确列语义没有通过独立差分验证。铁剑、青铜剑的旧测试绑定不属于本次验收，换包后还须分别核对帧区间，不能据此声称它们正常。

## 从原画到动画的正确顺序

1. **先做一张游戏比例的代表帧。** 本次由用户提供黑金披风人物原画，制作人物、金色纵向光束和地面法阵，再加入贯穿主体但不遮挡关键部位的青蓝色小号草书竖排文字。单帧经用户确认后才扩为动画；不在未验收的图上批量换字、放大光效。
2. **始终保留透明 PNG 的像素和 alpha。** 明月原包 PNG 可见细光、半透明粒子；经某次 WZL 编辑器导出 BMP 后再导入，实机变暗、变粗且模糊。问题不应仅归咎于引擎或 PAK 格式。不要把有透明度的特效帧走 BMP 中转；如需编辑，逐帧检查 32 位带 alpha 的 PNG、透明背景、边缘与半透明像素。
3. **用供体学习节奏，不把供体帧数误认为本作帧数。** 明月参考包存在不同长度的连续帧组；其中 `00560–00592` 为 33 帧组。此次候选根据供体亮度起伏取样为一个 12 帧周期，固定人物、法阵和文字的位置，只变化光束、金色流光和粒子。它是按参考动作规律制作的**自有 12 帧**，并非逐像素复刻原 33 帧，也不是将同一张图复制 12 次。
4. **统一画布和原点。** 本次 12 张都是 `600×700` 的带透明度 PNG，编号连续 `00000.PNG` 至 `00011.PNG`。批量前后检查宽高、色彩/alpha、四角透明、文字与人物基准位置、相邻帧差异；不能靠每帧大幅平移整个人物制造动感，否则游戏里会抖动和偏位。
5. **在最终游戏中判断视觉质量。** 透明底编辑器预览和深色底合成图只用于发现技术错误。半透明像素在实际地图纹理、引擎混合方式和尺寸下可能变淡或变厚；先试一件，再决定色彩、粗细与坐标。不要以静态预览替代实机。

## 资源交付和原生绑定

1. 在临时中文工作区保存候选及对照图；经审核后，用现有原生 PAK 编辑器按连续顺序导入到专用资源包。导入后在编辑器回看**实际帧号、帧数、透明度及首尾帧**，再填写起始图片和数量。不要只根据文件名猜包内编号。
2. 保持 `EffectImageList.txt` 原有行顺序，只在末尾注册新资源并按零基索引读取当前端编号。资源逻辑名称、客户端 `data` 下的实际 PAK 和登录器制作目录中的补丁源必须指向同一版内容。PAK 密码只在本地现有登录器配置中管理，**不提交到 Git**。
3. 通过 M2 原生「查看 → 列表信息2 → 光柱特效」管理定义和物品绑定；两栏各有保存动作。若按已验证的 GUI 结果做等价文件操作，必须先备份、保持原编码和 CRLF、最小改动并回读；不得把 `EffectList/EffectItemList` 的内观特效链与这里的 `PillarOfLightEffect/PillarOfLightEffectItemList` 混用。
4. 本次采用光柱号 `50001`、目标端资源号 `37`、包内起始 `0`、数量 `12`、速度字段 `100`。先用木剑一件验证可见性；坐标校正仅改 Y，最终为 X=`0`、Y=`-270`。以后换尺寸、主体位置或绘制标记，坐标重新以单件实机为准。
5. **客户端补丁源变更时同步检查登录器。** 本次曾出现登录后 `老方.Pak` 回退：当时运行的登录器早于新补丁源生成，重新登录会恢复旧包。用户从实际制作工具重生成登录器后，客户端保持新版 PAK，光柱才在游戏中显示。不能把“本地手动导入成功”当成登录后仍会保留；也不能说每次只改服务端坐标都必须重生成登录器。
6. 由用户完成游戏验收：单件掉落时看主体、文字和底座；移动角色及鼠标，按**物品图标/真实落点**而非红色名称文字估计偏移；再检查完整动画周期、拾取后消失、重丢出现及未绑定物品对照。若只测了显示和位置，结论就停在这两项。

## 复做前的最小核对

- 一张代表帧先验收；从 PNG 到 PAK 不经过失去 alpha 的 BMP 中转。
- 每帧画布、原点和文字稳定；光与粒子有真实变化；帧号连续且数量与定义一致。
- `物品名 → 光柱号 → 定义资源号 → EffectImageList 零基项 → 客户端 PAK → 包内帧区间` 逐环闭合。
- 登录器补丁源与客户端 PAK 版本一致；发生自动回退时先查制作时间和更新链，不反复叠加视觉补丁。
- 先备份，改单件，回读并在游戏地图实测；坐标/绘制标记只一次改变一个假设。文件哈希一致、编辑器预览好看不等于实机通过。

本次成功的关键不是某个固定滤镜或固定坐标，而是**原画单帧确认 → 保真 PNG 多帧 → 原生包及登录器交付 → 目标端零基映射 → 单件游戏验收校准**这一整条闭环。
