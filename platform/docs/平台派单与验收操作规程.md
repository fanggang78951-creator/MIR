# 平台派单与验收

用户提出功能用途并填写总控指定的中文文件。总控先看当前功能卡与发布记录，再派单；旧聊天和历史脚本只用于追溯。

1. 从 `catalog/current-release.json`取得成套GUI/CLI。核对可执行文件、源码和包指纹。启动入口会检查这些指纹，失败时停止。
2. 用 `project-list --query 关键词`匹配能力，再用 `project-card --id 功能ID`读取功能卡。缺文件、缺路由或当前版本没有验收证据时，不作为已验收能力派单。
3. 指定中文表格/TXT，引用文件中的说明页和对应接口。内部标签、编号和目标映射由总控/平台负责，不让用户从旧聊天寻找。
4. 用 `project-task --id 功能ID --task-id 原任务编号 --server 目标目录 --client 客户端目录 --validation`生成独立验证任务。正式能力验证完成后可去掉`--validation`；新代码不能沿用旧版验收。
5. 预检任务单只授权预检。根目录、输入、辅助参数、发布版本或目标内容变化，都重新预检。制作窗口只提交预检报告、精确差异和恢复方法。
6. 总控根据具体差异派发安装任务，写明允许修改路径和候选/真实目标。高风险操作按用户规定统一确认。不得笼统授权任意目标写入。
7. 独立验收核对冻结CLI、产物、实际文件、事务收据、重复零变更、冲突和回滚；游戏实效另列结果。
8. 总控更新同一任务记录和相关功能卡。执行窗口不改公共交班、索引、最近指针；不自行改平台源码或复制历史成品。

## 三个常驻任务

- 平台能力与资料整理：功能卡、输入说明、历史证据与归档候选。
- 平台制作与能力维护：按平台执行；缺能力时接受单独开发任务，在独立候选目录修复。
- 平台独立验收：只根据交付任务单、当前功能卡和填写输入，核对平台执行结果。

任务ID和任务窗口对应关系保存在`catalog/task_roles.json`。同一需求重试必须复用任务ID。

该文件的`task_id`记录本次设立分工的需求。后续新需求由总控另定唯一编号，在`project-task --task-id`和执行任务单中明确传入；不能每次复制验证任务单就另写公共交班。

## 验收记录

功能卡注释位于`catalog/feature_annotations.json`，仅保存说明与证据引用，不重复保存业务参数。总控核实真实游戏结果后，才能设置`game_verified`，记录证据文件SHA256和该卡列出的全部`required_fingerprints`。缺任一指纹或文件变化，系统自动取消当前可派单状态。

冻结发布存在时，必需指纹包含`catalog/current-release.json`，因此更换GUI/CLI、运行依赖或发布身份也会使旧验收失效，不能只用相同源码继续沿用验收。发布记录属于不可变证据；归档日志按相对证据索引查找，不通过改写旧发布记录修正路径。

`accepted_input_hashes`记录被验收的输入实例；用户合法修改配置后只要求重新预检，不冒充该配置已经通过游戏验收。源码、路由、包和依赖变化必须重验对应能力。

历史材料按归档计划压缩并逐文件核对原字节，保留恢复映射和当前有效引用。失败细节可以归档，未解决的问题必须保留在当前功能卡。
