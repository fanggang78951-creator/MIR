# 怪物库 V3：翎风引擎闭包设计

日期：2026-08-23  
状态：用户已确认（2026-08-23）  
适用平台：`E:\XuanYuanDevPlatform`  
目标引擎：翎风 / LFM2

## 1. 背景与已验证事实

现有怪物库 V2 将所有供体怪物统一按 `Appr//10+1` 定位 Mon 图库，并用一个 PAK 或一对 WZL/WZX 代表“完整动作补丁”。这个模型只适合普通 Appr 怪物，无法表达 RaceImg=156 自定义怪物所需的引擎闭包。

星辰怪13已经在当前目标端完成游戏验收，证明 RaceImg=156 怪物至少需要以下完整链路：

1. 目标 Monster 数据库中存在唯一同名行。
2. `Race`、`RaceImg`、`Appr` 与目标模型匹配。
3. `Mir200\Envir\SmartMonster\<怪物名>.ini` 与数据库名称逐字符一致。
4. INI 内的 `ActionFile`、`EffectFile` 等资源号按供体 `EffectImageList.txt` 的零基编号解析。
5. 迁入目标端时重新分配目标零基编号，并重写 INI 中所有非负资源引用。
6. 目标客户端存在对应动作资源；本次黄金样本是独立 WZL/WZX。
7. M2 加载新 INI 后，还必须生成新的 `自定义怪物.dat`，由 MakeGameLogin 集成并重新生成登录器。
8. 最终验收必须覆盖身体、站立、行走、攻击、受击和死亡动作。

因此，V3 的基本单位不再是“一个外观号”或“一个补丁文件”，而是“一个可由翎风引擎加载的怪物闭包”。

## 2. 目标

1. 从任意翎风/LFM2供体端读取怪物时，优先按供体引擎配置识别真实依赖。
2. 普通 Appr 怪物和 SmartMonster 自定义怪物使用不同解析器。
3. 只有依赖闭包完整、冲突可控的模型才能进入默认随机池。
4. 用户的批量生成表继续只要求名称、等级、经验、血量、防御、魔防、攻击、命中、颜色等基础属性。
5. 模型库编号可以留空；留空时从“目标兼容且闭包可部署”的模型中进行稳定随机选择。
6. 不把供体怪物的血量、攻击、防御、经验或特殊能力当作新怪属性来源。
7. 数据库、SmartMonster INI、EffectImageList、客户端资源和登录器要求进入同一预检、事务、回滚及验收报告。
8. 资源难以解析、闭包不完整或特殊能力过于复杂时，安全跳过，不强行迁移。

## 3. 非目标与边界

1. V3 不新增刷怪点，不修改刷怪位置、数量、首刷或刷新间隔。
2. V3 不生成爆率，不修改 MonItems、NPC、任务、地图或AI脚本。
3. V3 不自动打开、关闭或操作 M2、GameCenter 和游戏客户端。
4. V3 第一版不反向破解未知 PAK 密码，不把无法解析的 BMP 重建为怪物帧。
5. V3 第一版不自动生成 M2 的二进制 `自定义怪物.dat`；平台负责检测、引导和验收该人工步骤。
6. V3 第一版不迁移供体 SmartMonster 中的额外攻击、召唤、附加状态或保护增益。发现复杂能力时标记为不可进入默认随机池。
7. V2 历史 PAK 兼容重封和按 Appr 猜测 RaceImg=156 主体资源的路线只保留为历史证据，不进入 V3 运行路径。

## 4. 引擎模式分类

每条供体怪物记录必须先分类，再选择解析器。

### 4.1 `standard_appr`

适用于不要求同名 SmartMonster INI 的普通怪物。

- 按引擎已验证的 Appr 规则定位 Mon 图库。
- 资源可以是完整 PAK，或成对 WZL/WZX。
- PAK 必须有唯一密码规则；WZL 必须有对应 WZX。
- 目标端存在同号同哈希资源时可以复用；同号异内容时不得覆盖公共资源。

### 4.2 `smartmonster`

以下任一条件命中时进入 SmartMonster 解析：

- 供体存在与 Monster 名称完全一致的 `SmartMonster\<怪物名>.ini`；或
- 引擎字段表明该怪物属于自定义怪物链，例如当前已验证的 `RaceImg=156`。

SmartMonster 必须具备：同名INI、供体 EffectImageList、所有非负资源引用、资源实体及动作验证证据。若引擎字段要求 SmartMonster 但同名INI缺失，直接标记闭包缺失。

### 4.3 `unsupported`

以下情况进入不可部署状态：

- 引擎模式无法识别；
- INI 依赖未知资源类型；
- 资源、伴随索引或密码缺失；
- 基础动作段缺失或越界；
- 启用了第一版禁止迁移的复杂服务端能力；
- 供体资源在扫描期间发生哈希漂移。

## 5. V3 数据模型

V3 使用新的 `catalog.sqlite` 模式版本，不原地猜测升级 V2 记录。

### 5.1 `monsters`

保留现有 Monster 数据字段和展示字段，新增：

- `engine_mode`：`standard_appr`、`smartmonster` 或 `unsupported`。
- `closure_status`：见第6节。
- `closure_hash`：Monster模型字段、INI、依赖清单和资源哈希共同计算的稳定摘要。
- `smart_ini_path`、`smart_ini_hash`：SmartMonster 本地化文件证据。
- `source_effect_list_path`、`source_effect_list_hash`：供体零基解析依据。
- `resource_manifest_json`：资源引用映射和动作验证摘要。
- `login_policy`：`none` 或 `custom_monster_dat_required`。
- `capability_policy`：`basic_melee` 或拒绝原因。

### 5.2 `monster_dependencies`

一只怪物可以拥有多个依赖，每个依赖记录：

- 供体零基资源号；
- EffectImageList 原始条目；
- 资源类型：PAK、WZL/WZX或后续适配器类型；
- 本地化源文件、伴随文件、大小与SHA256；
- PAK密码规则（如适用）；
- 动作段或可读取帧证据；
- 目标端命名策略和是否允许按哈希复用。

### 5.3 `meta`

记录模式版本、扫描时间、供体数据库、自动识别出的供体服务端根目录、供体客户端路径、目标路径、解析器版本和本地化状态。

## 6. 闭包状态

界面和随机池使用明确状态，禁止再用“有缩略图”等同于“有补丁”。

- `ready_verified`：静态闭包完整，动作帧可验证，可进入默认随机池。
- `ready_opaque`：引擎闭包和文件完整，但资源容器不透明；只能显式选择，不能进入默认随机池，部署后必须单怪验收。
- `existing`：目标服已有同名怪物。
- `incomplete`：缺INI、资源、伴随文件、密码或动作段。
- `complex_ability`：供体包含第一版不迁移的特殊服务端能力。
- `conflict`：目标端存在同名异内容资源、重复资源登记或其他不可安全覆盖冲突。
- `unsupported`：资源类型或引擎模式暂不支持。

预览缩略图状态独立保存，不参与闭包是否可部署的判断。

## 7. 供体扫描流程

1. 用户继续选择供体怪物DB和客户端data；平台根据 `...\Mud2\DB\ApexM2.DB` 自动推导供体服务端根目录，并在界面只读回显。
2. 若目录结构不符合翎风标准，预检阻止并允许高级用户显式指定供体服务端根目录；默认表单不新增必填项。
3. 读取供体实时 `!setup.txt`、Monster数据库、SmartMonster目录、EffectImageList和客户端资源。
4. 对每只怪物进行引擎模式分类。
5. 普通怪物走 Appr 解析器；自定义怪物走 SmartMonster 解析器。
6. SmartMonster 解析器按供体 EffectImageList 的物理行零基计数解析资源号；不得把零基号当作物理行号，也不得因空白或编码规范化改变索引。
7. 收集 `ActionFile`、`EffectFile`、`EffectFile2`、`Fly_File`、`FlyEff_File`、`Self_File`、`SelfKeep_File`、`Explosion_File`、`Target_File`、`HPFile` 等所有非负引用。
8. 将供体INI和资源复制到平台资产库，复制后逐文件哈希回读。
9. 对可读取的 WZL/WZX 验证站立、行走、攻击、受击、死亡基础动作，检查索引边界、空帧和允许的怪物帧类型。
10. 检查 `ServerAttack`、`Additionals`、`CallMonster` 和 `Protect` 等服务端能力。第一版只允许基础近战安全样本进入默认随机池。
11. 生成闭包摘要并写入V3目录；扫描只读供体与目标业务文件。

## 8. 模型选择与属性规则

### 8.1 新怪物

- 模型库编号留空：仅从 `ready_verified` 且目标端兼容的模型中稳定随机选择。
- 显式填写模型库编号：允许选择 `ready_verified`；`ready_opaque` 必须在预检中明确提示单怪验收要求。
- 不再以 `模型Appr` 作为默认用户入口；旧表存在该列时只用于兼容校验。
- 新怪数据库行从目标端固定的中性基础怪物模板取得非模型默认值，再写入用户表格基础属性。
- 只从模型闭包迁入引擎必需字段，例如 Race、RaceImg、Appr及明确列入白名单的动作控制字段。
- 禁止复制供体的血量、攻击、防御、经验、特殊攻击、召唤和状态能力。

### 8.2 目标端已有同名怪物

- 表格模型留空时，只更新用户填写的基础属性并保持现有模型与闭包。
- 显式换模时，必须部署新闭包并在同一事务中更新模型字段。
- 目标端存在多个同名行时阻止操作。

### 8.3 稳定随机

随机选择继续使用工作簿哈希、行号和怪物名称形成稳定种子；同一表格重复预检必须得到同一模型。候选池变化时报告自动改选原因。

## 9. 目标端部署事务

### 9.1 普通Appr模型

沿用V2的安全能力：检查公共资源冲突、复制完整资源、同步PAK密码规则、写Monster数据库、逐文件回读和事务回滚。

### 9.2 SmartMonster模型

预检按以下顺序构建候选，不直接写生产端：

1. 为每个依赖在目标 `EffectImageList.txt` 分配新的零基编号。
2. 若目标已存在同哈希、同类型、可安全复用的独立资源，可复用现有编号；同名异哈希禁止覆盖。
3. 新资源使用稳定独立名，避免覆盖公共 Mon 图库。
4. 建立“供体零基号→目标零基号”完整映射。
5. 复制供体INI为目标怪物同名INI，并重写所有非负资源引用。
6. 重写后再次解析INI，确认不存在供体资源号残留或未纳入依赖。
7. 验证目标候选资源和基础动作。
8. 构建数据库候选、EffectImageList候选、同名INI候选和客户端资源候选。

事务提交前必须确认 M2 和目标客户端未运行，并重新检查所有目标文件的预检前哈希。任一写入或回读失败时，按反向顺序逐字节回滚。

回执必须包含：怪物名、引擎模式、闭包哈希、目标零基映射、数据库变更、INI、客户端资源、EffectImageList前后哈希、登录器门禁和回滚命令。

## 10. 登录器集成门禁

只要事务新增或修改 SmartMonster INI、EffectImageList或自定义怪物资源，计划就设置：

- `requires_custom_monster_dat=true`
- `requires_login_regeneration=true`
- 最终状态为“服务端已部署，待客户端集成”，而不是“全部完成”。

平台在安装后显示固定引导：

1. 在M2怪物设置中生成新的 `D:\MirServer\Mir200\自定义怪物.dat`。
2. 在 MakeGameLogin 的“集成配置”中勾选“自定义怪物配置”。
3. 选择该 DAT，保存配置并生成目标客户端登录器。
4. 平台只读复核 MakeGameLogin `Config.ini` 中的开关和路径。
5. 新登录器最后写入时间必须晚于本批INI、EffectImageList和DAT。
6. 游戏内完成单怪身体和五类动作验收后，才能标记为游戏验证通过。

V3 第一版不自动操作上述UI，也不自行生成二进制DAT。

## 11. 界面设计

保留用户熟悉的“怪物库”页面和表格流程，减少操作变化。

### 11.1 扫描区

- 继续显示供体怪物DB、供体WZL data、供体PAK data、供体pak.txt、目标服务端、目标客户端data。
- 新增只读“供体服务端根目录（自动识别）”回显，不新增默认必填项。
- “扫描明月并重建怪物库”改名为“按引擎规则扫描供体并重建V3怪物库”。

### 11.2 列表区

主要列改为：预览、库编号、怪物名称、引擎模式、Appr、闭包状态、依赖数量、登录器要求、说明。

状态筛选改为：默认可随机、可显式选择、本端已有、闭包不完整、复杂能力、全部。

### 11.3 预检与安装报告

报告新增：

- 普通Appr模型数量；
- SmartMonster模型数量；
- INI数量；
- 资源依赖数量；
- EffectImageList新增条目和目标零基号；
- 需要重新生成DAT和登录器的怪物；
- 跳过原因；
- 属性是否来自用户表格、模型字段是否来自闭包。

按钮名称可继续保持“预检选中”“一键植入”“一键同步怪物”，但确认框必须准确描述本次将写入的引擎闭包内容。

## 12. 错误处理与安全门禁

1. 不允许同名怪物多行、不允许同一依赖映射到多个不同目标资源。
2. EffectImageList 使用精确编码和换行回写，不重排历史行。
3. 预检后任一目标文件发生变化，提交立即停止。
4. 供体文件在扫描或构建候选期间哈希变化，候选作废。
5. M2、目标客户端或资源编辑器运行时阻止正式提交和回滚。
6. 公共资源同名异内容时不覆盖，改用独立资源名；无法安全改名时跳过。
7. 已部署目标只有“完整一致”和“冲突”两种可复核状态，不把部分文件存在视为成功。
8. 回滚前验证部署后哈希；文件被其他任务修改时禁止整文件回滚并报告人工处理路径。

## 13. V2迁移策略

1. V3使用新的模式版本；检测到V2时不自动解释为V3闭包。
2. 重建前备份V2 `catalog.sqlite`、当前界面配置和相关平台代码。
3. 已本地化的大资源按哈希复用，禁止为升级无意义复制整库。
4. V2历史候选、PAK兼容重封和失败脚本不进入V3默认扫描或安装路径。
5. V3扫描完成后保留V2回滚入口，直到V3隔离验证和平台打包回归通过。

## 14. 测试设计

### 14.1 黄金样本

以已游戏验证通过的星辰怪13链建立固定夹具：

- Race=156、RaceImg=156、Appr=1123；
- 供体同名SmartMonster INI；
- 零基78解析为Mon7.wzl；
- 12处ActionFile和1处EffectFile重写；
- 站、走、攻、伤、死共224张有效播放帧；
- 只含基础近战能力。

### 14.2 失败测试

必须覆盖：

- RaceImg=156缺同名INI；
- EffectImageList差一位；
- 资源引用未全部重写；
- WZL缺WZX、PAK缺唯一密码；
- 动作帧空、越界或类型错误；
- 特殊攻击、召唤、状态和保护能力；
- 目标资源同名异哈希；
- 目标EffectImageList预检后漂移；
- 登录器未勾选自定义怪物配置；
- 新登录器时间早于DAT或INI；
- 事务中途失败后的逐字节回滚。

### 14.3 回归测试

- 普通Appr怪物现有V2安全路径继续通过；
- 表格基础属性、名称颜色、已有怪保留模型继续通过；
- 模型留空稳定随机；
- 新怪不继承供体属性；
- 不新增MonGen、不修改爆率；
- 重复预检幂等；
- 完整平台测试、编译和便携版构建通过。

## 15. 实施分期

### 阶段1：V3闭包模型与只读扫描

建立V3 schema、引擎模式分类、SmartMonster解析器、资源依赖本地化和黄金测试。此阶段不具备正式安装能力。

### 阶段2：候选构建与事务安装

实现目标零基分配、INI重写、独立资源命名、候选验证、事务提交、回读和回滚。

### 阶段3：表格与界面接入

接入基础属性白名单、稳定随机、现有怪保留模型、V3列表列项、预检摘要和登录器门禁。

### 阶段4：隔离验收与平台发布

使用隔离服务端和客户端完成普通Appr与SmartMonster两条完整事务；运行全量回归并打包新平台。正式端默认零写入，后续由用户选择一只新怪做平台一键验收。

## 16. 完成标准

V3平台修复只有同时满足以下条件才能标记完成：

1. V2根因已有自动化失败测试保护。
2. 星辰怪13黄金闭包可由通用V3解析器得到，不依赖星辰怪13专用常量脚本。
3. 普通Appr和SmartMonster两条路径均有隔离事务、幂等预检和逐字节回滚证据。
4. 表格生成的新怪只使用用户基础属性和引擎必需模型字段。
5. 随机池不会选中闭包不完整、复杂能力或未验证的模型。
6. 平台能准确提示并核对DAT与登录器集成，不再只提示“重新生成登录器”。
7. 现有平台相关测试及全量回归通过。
8. 当前服务端、MonGen、爆率和已验收的星辰怪13在平台开发期间保持不变。
9. 使用V3平台新生成的一只测试怪完成身体和五类动作游戏验收后，才将V3标记为游戏验证完成。
