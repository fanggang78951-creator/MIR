# 玄渊第三方批量做装备平台设计

## 目标

把 `D:\MirServer旧\AI_Handoff\tools\xy_equip_maker` 中已经验证、好用的装备生成能力迁入 `D:\XuanYuanDevPlatform\做装备`，并合并到现有成果植入平台 GUI。工具只暴露批量 XLSX 做装备入口，保持原装备字段、原生 Element 属性、固定三表属性和脚本属性定义不变，能够对任意同引擎第三方服务端及其客户端进行预检、事务安装和逐字节回滚。

## 明确边界

### 必须保留

- `XuanYuanItems.xlsx` 现有工作表、列名、列顺序兼容能力和空值语义。
- `script_properties.json` 中全部属性名称、单位、变量、锚点和脚本出口。
- StdItems 字段映射、武器攻速反号规则、绿字颜色和“隐藏触发”显示规则。
- ItemDescList、ItemRuleList、GroupItemList 固定三表路线。
- 神力倍攻、打怪伤害、暴击伤害、人物爆率、最大爆率、固定切割、首刀斩杀、尾刀斩杀、鞭尸概率等现有脚本属性逻辑。
- Items、StateItem、DnItems 三套同编号静态图标链路和资源映射校验。
- 原工具的重复装备名阻止、模板不存在阻止、部位/StdMode 冲突阻止和资源链不完整阻止。

### 不再暴露

- 单件 TXT 图形入口和单件“直接生成”入口。
- 不允许用户切换目标的硬绑定方式；`D:\MirServer` 只保留为可修改的初始目标。
- 历史测试装备、临时探针、批量输出目录和失败路线作为运行依赖。

单件核心函数可作为批量引擎内部实现保留，但用户界面和公开 CLI 只允许 XLSX 批量预检与安装。

## 目录结构

```text
D:\XuanYuanDevPlatform\做装备
├─ src\xyequip                 独立装备领域核心
├─ templates                   正式 XLSX 模板和示例
├─ profiles                    属性注册表、资源映射与已验证槽位
├─ docs                        搬迁后的使用说明和属性契约
├─ evidence                    原始哈希、交班证据和验证报告
├─ legacy_archive              不参与运行的历史样例及失败记录
├─ outputs                     每次预检生成的候选植入包
└─ backups                     装备事务备份
```

平台通用代码继续位于 `src\xydp`。装备核心不得导入某个服务端目录中的 Python 文件，也不得读取 `library\sources\legacy_ai_handoff` 作为运行依赖。

## 目标与路径模型

装备页面复用平台“目标管理”选择的服务端和客户端根目录，并额外选择：

- XLSX 装备源表。
- 可选素材根目录。
- 输出目录，用于保存预检报告和候选植入包，默认 `D:\XuanYuanDevPlatform\做装备\outputs`。

批量做装备页面的服务端目标默认填入 `D:\MirServer`，装备安装目标也默认是该目录。如果该目录不存在或不是 LFM2 服务端，页面保留路径但预检失败并提示用户重新选择；不得猜测其他目录。用户选择另一个同引擎服务端后，数据库、三表、QFunction、备份、安装收据和回滚全部跟随新目标。

除 GUI/CLI 的这一项用户偏好默认值外，所有实际路径由调用参数或平台目标对象提供。装备核心、属性注册表、模板和事务实现不得依赖 `D:\MirServer` 必须存在，也不得把 `D:\11周年` 或 `D:\素材文件夹` 作为固定运行路径。说明文档允许把旧路径写为“历史来源”，示例命令必须显式传入目标参数。

目标识别沿用平台 LFM2 检查：必须存在 `Mir200\M2Server.exe`、`Mir200\Envir`、`MapInfo.txt`。数据库定位为服务端根下 `Mud2\DB\ApexM2.DB`；客户端静态资源定位为客户端根下 `data` 或用户直接选择的 data 目录。无法唯一定位时阻止预检，不猜路径。

## 属性保真契约

搬迁前生成 `evidence\source_contract.json`，记录下列原文件 SHA-256：

- `xy_equip_maker.py`
- `xy_batch_equip_maker.py`
- `script_properties.json`
- `input\XuanYuanItems.xlsx`
- `D:\MirServer旧\AI_Handoff\装备源表` 中所有 XLSX 文件

搬迁测试必须证明：

1. 新旧 `script_properties.json` 规范化 JSON 完全相等。
2. 新旧 XLSX 表头、字段顺序和示例行读取结果完全相等。
3. 同一 XLSX 行在旧核心和新核心的 dry-run 结果中，StdItems 字段、三表行、脚本属性分支和资源请求完全相等；仅绝对路径、时间戳和事务号允许不同。
4. 不新增、不删除、不改名任何现有属性。

## 架构

### 1. XLSX 读取层

负责读取现有 `XuanYuanItems.xlsx`，校验列名并转换为与原 `xy_batch_equip_maker.py` 一致的装备记录。它不访问服务端、不生成 SQL、不修改文件。

### 2. 装备编译层

复用原 `xy_equip_maker.py` 的字段映射和属性生成逻辑，将每行编译为不可变候选结果：StdItems 行、ItemDescList 行、ItemRuleList 行、GroupItemList 行、QFunction 锚点分支、静态资源请求和诊断信息。批量中任意一行失败时整批失败。

### 3. 第三方目标适配层

只负责从用户选择的服务端/客户端根目录读取目标文件和现有占用，不包含装备属性算法。检查数据库表结构、装备重名、Idx、模板、固定表键、脚本锚点、资源编号和 WZL/WZX 配对状态。

### 4. 装备事务层

把编译结果转换为平台安装计划。预检阶段只在内存和 `做装备\outputs` 中生成摘要，不写目标。安装阶段先备份所有受影响文件，再在临时副本完成 DB 与文本合并、哈希验证，全部通过后原子替换。失败恢复安装前字节。

数据库不能通过平台现有的单文件文本操作处理；装备事务必须把 ApexM2.DB 当作单个二进制受影响文件，在临时数据库副本中执行 SQL，完成结构、行数和目标装备校验后再原子替换。

### 5. GUI 集成层

现有 GUI 新增“批量做装备”页面，包含：

- XLSX 选择与模板打开入口。
- 服务端、客户端和素材路径摘要；服务端初始值为 `D:\MirServer`，允许浏览并替换为第三方服务端。
- “检查源表”按钮。
- “生成预检”按钮。
- 按装备列出的错误/警告及受影响文件摘要。
- “确认安装”按钮；只有预检成功且用户明确确认时启用。
- 最近装备事务与回滚入口。

页面不提供单件 TXT 选择、不提供直接修改现有装备的快捷按钮。

## 数据流

```text
选择第三方服务端/客户端
        ↓
读取 XuanYuanItems.xlsx
        ↓
保持原属性映射进行批量编译
        ↓
扫描第三方目标冲突和资源占用
        ↓
生成零写入预检及候选植入包
        ↓ 用户明确确认
备份 DB、三表、QFunction、客户端资源
        ↓
临时副本应用并验证
        ↓
原子替换 + 安装收据
        ↓
可逐字节回滚
```

## 与战斗成果包的关系

脚本属性仍使用原 `script_properties.json` 的统一出口，不为每个新服务端复制旧服完整 QFunction。装备预检先检查成果植入平台的 `xy.combat.core` 及所需战斗子包契约：

- 目标已有平台锚点时，只插入该批装备的受管分支。
- 目标缺少所需公共契约时，预检报告明确列出必须一并安装的成果包。
- 不自动使用历史行号或中文目录定位旧服脚本。
- 不创建与公共战斗包重复的变量初始化或伤害结算框架。

## 客户端资源策略

保留原工具已验证的静态图标处理能力和 raw-clone 路线，但必须参数化客户端 data 路径。Items、StateItem、DnItems 的 WZL/WZX 六个文件作为一个资源事务：任意一库缺失、编号不一致、源帧为空或类型不受支持，整批阻止。

武器/衣服动作帧不因本次迁移扩大能力。原工具已支持并已验证的资源映射继续使用；历史未完成的高 Shape、新动作帧逆向和 type259/type2309 通用解码不得宣称完成。

## 迁移规则

1. 先把确认的正式文件复制到 `做装备` 并记录源/目标 SHA-256。
2. 在平台副本中完成路径参数化和测试，旧文件在此期间保持不动。
3. 验证通过后，将旧 `tools\xy_equip_maker` 正式文件移动到平台；旧目录只留下迁移说明和新位置指针。
4. `装备源表` 中 XLSX 正式母版移动到 `做装备\templates`；平台同时保留只读原始哈希证据。
5. 历史 output、测试装备和失败探针移动到 `做装备\legacy_archive`，不进入运行路径。
6. 每个移动项写入迁移登记：原路径、目标路径、原始哈希、分类、是否运行依赖和验证状态。

## 安全与错误处理

- M2Server.exe 正在运行时禁止安装数据库和服务端文件。
- 客户端进程占用资源文件时禁止写客户端。
- 重名装备、重复 Idx、模板不唯一、目标表结构异常、三表唯一键冲突、QFunction 锚点歧义或 WZL 编号冲突均阻止整批。
- 预检报告必须区分错误与警告；错误存在时安装按钮禁用。
- 默认不覆盖已存在装备；本期不暴露原批量工具的“修改现有装备”入口。
- 安装收据记录 XLSX 哈希、属性契约哈希、目标文件安装前后哈希、备份路径和装备名称列表。

## 测试与验收

### 自动测试

- XLSX 表头和行解析与原工具一致。
- 全部脚本属性注册表规范化内容一致。
- 原生 Element、固定三表属性、脚本属性分别生成正确结果且互不覆盖。
- 多件装备批量编译、重名、模板缺失、部位冲突、资源冲突和任意行失败整批中止。
- 代码和运行配置不含固定旧服务端/客户端路径。
- 默认目标为 `D:\MirServer` 时能够预检和安装；替换为其他同引擎根目录时产生等价计划，证明默认值不是依赖。
- 预检零写入。
- 临时 DB 应用失败不改变目标。
- 安装、幂等检测、手工修改阻止和逐字节回滚。
- 空白同引擎夹具与已有第三方脚本夹具。

### 实际验收

1. 使用迁入的原 XLSX 模板在独立测试服生成一小批装备。
2. M2 启动无数据库或脚本错误。
3. 验证基础属性、固定绿字、面板数值、脚本属性、三套静态图标及地面显示。
4. 验证神力、怪伤、爆伤、爆率、最大爆率、首尾刀和鞭尸互不覆盖。
5. 回滚后 DB、三表、QFunction 和客户端六个资源文件与安装前逐字节一致。

未完成游戏内验收前，第三方装备植入功能保持 candidate；不能仅凭静态测试标记 verified。
